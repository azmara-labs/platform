`@azmr/ui` is themed with CSS custom properties: the [design tokens](/docs/guide/tokens). You can override a token in plain CSS, or call `createTheme` to derive a whole accessible set from your brand colours. The examples with an `// =>` line on this page are run by the docs tests, so the output shown is what the package returns.

## Change the brand colour with createTheme

```ts example=brand result=changed
import { createTheme } from "@azmr/ui/theme";

const theme = createTheme({ primary: "#1E88E5", radius: "0.5rem" });
const changed = Object.keys(theme.cssVariables);
// => ["--primary","--primary-foreground","--ring","--sidebar-primary","--sidebar-primary-foreground","--sidebar-ring","--radius"]
```

Setting `primary` sets six variables: the colour, the text on it, the focus ring, and the same three for the sidebar. Each colour value is a `light-dark()` pair, so it follows the page's mode. These are the options:

Every option is optional and keeps its default when left out. Colours are `#rgb`, `#rrggbb`, `oklch(L C H)` or `{ l, c, h }`.

### What it guarantees

The colour you pass is a starting point. `createTheme` moves its lightness, and picks white or near-black text, until these hold in both light and dark mode:

- Each `-foreground` is at least **4.5:1** on its colour, **including on a solid button's hover surface**. A button blends with the page on hover, which can pull a colour that only just passes below 4.5:1, so the derivation checks the blended colour too.
- `success`, `info` and `destructive` are also readable as **text** on the page and on cards (`Text tone`, form errors). `warning` is a yellow surface, so it gets a separate, darker `--warning-text` for text.
- The focus ring is at least **3:1** on the page and on cards.

Because of this, the result can differ from your input. The light-mode primary above is darker than `#1E88E5`, so that white text on it stays readable when the pointer is over it. A very light brand colour such as `#FFEB3B` goes the other way and gets dark text:

```ts example=light-brand result=foreground
const theme = createTheme({ primary: "#FFEB3B" });
const foreground = theme.cssVariables["--primary-foreground"];
// => "light-dark(oklch(0.145 0 0), oklch(0.145 0 0))"
```

Print `theme.cssVariables` to see what you get. The package's tests check these ratios for a range of brand colours, and the [token reference](/docs/guide/tokens#contrast-the-tests-guarantee) lists the ratios for the default tokens.

### Invalid input

`createTheme` validates every option and throws an `Error` that names it, because its output is CSS:

```ts example=invalid result=message
let message;
try {
  createTheme({ primary: "blue" });
} catch (error) {
  message = error.message;
}
// => "createTheme: primary must be #rgb, #rrggbb, oklch(L C H) or { l, c, h }; got \"blue\""
```

`radius` must be a number in `rem` or `px`, `font` must be a short font-family list (letters, digits, spaces, commas, quotes, dots, hyphens and underscores, 200 characters at most), and `density` must be `compact`, `comfortable` or `spacious`.

## Set light and dark separately

Beyond the brand colour, `createTheme` can set every colour **role**, and each role has its own light and dark value. A role is a named colour that components use, such as `background` or `sidebar-accent`. Components only use roles and never check the mode, so changing a role changes every component that uses it. There are 35:

| Group | Roles |
|---|---|
| Page and surfaces | `background`, `foreground`, `card`, `card-foreground`, `popover`, `popover-foreground`, `muted`, `muted-foreground`, `accent`, `accent-foreground` |
| Actions | `primary`, `primary-foreground`, `secondary`, `secondary-foreground` |
| Status | `destructive`, `destructive-foreground`, `success`, `success-foreground`, `warning`, `warning-foreground`, `warning-text`, `info`, `info-foreground` |
| Lines and focus | `border`, `input`, `ring` |
| Overlay | `scrim` |
| Sidebar | `sidebar`, `sidebar-foreground`, `sidebar-primary`, `sidebar-primary-foreground`, `sidebar-accent`, `sidebar-accent-foreground`, `sidebar-border`, `sidebar-ring` |

`scrim`, the layer behind a modal, cannot be overridden. The chart colours are not roles.

### Three ways to define a theme

They build on each other, so use as few as you need.

1. **Derive.** Give only a `brand` colour (the alias of `primary`). Surfaces stay the neutral greys, and the brand appears on buttons, links and the focus ring. This is everything above.
2. **Tint.** Add `tint` and every neutral grey leans a few degrees toward the brand hue, so the app feels on-brand without coloured panels. `"brand"` is a light tint; a number from 0 to 0.04 sets the amount. A brand with no hue (black, white, grey) gets no tint.
3. **Override.** Set any role for one mode with `light` or `dark`. The other mode keeps the derived or default value.

Tint adds the neutral surface and sidebar roles after the six brand variables:

```ts example=tint result=surfaces
const theme = createTheme({ brand: "#0F4C5C", tint: "brand" });
const surfaces = Object.keys(theme.cssVariables).slice(6);
// => ["--background","--foreground","--card","--card-foreground","--popover","--popover-foreground","--muted","--muted-foreground","--accent","--accent-foreground","--sidebar","--sidebar-foreground","--sidebar-accent","--sidebar-accent-foreground"]
```

An override replaces one role in one mode, here a deep teal page in dark mode while light mode keeps its default:

```ts example=override result=background
const theme = createTheme({
  brand: "#0F4C5C",
  dark: { background: "oklch(0.2 0.03 220)" },
});
const background = theme.cssVariables["--background"];
// => "light-dark(oklch(1 0 0), oklch(0.2 0.03 220))"
```

Override values are `#rgb`, `#rrggbb` or `oklch(L C H)`. A role name that does not exist is an error, and so is `scrim`. In dark mode `border`, `input` and `sidebar-border` default to a translucent white, which stays unless you override it with an opaque colour.

### Contrast is checked

Once you use `tint`, `light` or `dark`, the finished theme is checked in both modes: every foreground on its surface at **4.5:1**, the status colours as text on the page and on cards at 4.5:1, and the focus rings at **3:1**. A theme that fails is rejected with a message that names the pair, so you cannot ship text that is unreadable:

```ts example=contrast-error result=message
let message;
try {
  createTheme({ brand: "#0F4C5C", light: { foreground: "#ffffff" } });
} catch (error) {
  message = error.message;
}
// => "Theme fails contrast checks:\n  - foreground on background (light): 1.00:1, needs 4.5:1"
```

The error is a `ThemeContrastError`, and its `issues` list has the role, the surface, the mode and both ratios. `validateTheme(options)` returns the same list without throwing, which is what an editor wants. Your override is never adjusted for you, because you asked for that exact colour. The colours `createTheme` derives for you (from `primary`, `secondary`, `success`, `warning`, `info` and `destructive`) follow the `background`, `card` and `popover` you override: they are derived for those surfaces, and a mode whose surfaces are dark is derived the way a dark mode is. A role you did not ask `createTheme` to derive stays at its default and is checked as it is. Options that existed before these (`primary`, `secondary` and the status colours on their own) are derived to pass and never throw.

Borders are not checked in this version: the default `border` and `input` do not reach 3:1 on the page, and in dark mode they are translucent. Making form-control borders meet that is a separate change to the tokens.

### A brand-coloured sidebar

If you paint the sidebar in the brand colour, `sidebar-ring`, the focus ring inside it, is derived for that sidebar and stays visible. `sidebar-primary`, the active item, is derived from the brand and ends up the same colour as the sidebar. The check catches the text colour. It does not check `sidebar-primary`, so set it yourself, with its foreground:

```ts example=sidebar-brand result=problems
const problems = validateTheme({
  brand: "#0F4C5C",
  light: { sidebar: "#0F4C5C" },
}).map((issue) => issue.message);
// => ["sidebar-foreground on sidebar (light): 2.08:1, needs 4.5:1"]
```

The `branded` preset below does exactly this: it sets `sidebar-foreground`, `sidebar-primary` and its foreground, `sidebar-accent` and its foreground, and `sidebar-ring`.

### Presets

`@azmr/ui/theme-presets` exports `THEME_PRESETS`: three ready-made themes for a made-up company, one for each way above. They are plain data, so use one as it is, or copy it and change the brand.

```ts example=presets result=names
import { THEME_PRESETS } from "@azmr/ui/theme-presets";

const names = Object.keys(THEME_PRESETS);
// => ["neutral","tinted","branded"]
```

The presets are frozen, so one part of an app cannot change what another part reads. Copy with `{ ...THEME_PRESETS.branded, brand: "#7B1FA2" }`.

### Store and share a theme

A theme config is plain JSON: the same options, plus an optional `version`, a `name` and `branding` (an `appName` and `logo`, `logoDark` and `favicon` images). `parseThemeJson` reads one from text you do not control, such as a database column or an upload:

```ts example=json result=config
import { parseThemeJson } from "@azmr/ui/theme";

const config = parseThemeJson('{"version":1,"brand":"#0F4C5C","tint":"brand"}');
// => {"version":1,"brand":"#0F4C5C","tint":"brand"}
```

It is strict because the result becomes CSS. It refuses text over 131,072 characters before parsing it, any key it does not know, and any value that is not exactly a colour, size or name it accepts. A `tint` needs a `brand` to lean toward, and a value of `undefined` counts as absent. Images must be `https:` URLs or `data:` PNG, JPEG or WebP images of at most 32,768 characters each, so three images and every role override always fit in the text limit; **SVG is not accepted**, because it can carry script. Every problem is reported at once:

```ts example=json-invalid result=message
let message;
try {
  parseThemeJson('{"brand":"red"}');
} catch (error) {
  message = error.message;
}
// => "Invalid theme config:\n  - createTheme: brand must be #rgb, #rrggbb or oklch(L C H); got \"red\""
```

To build an editing form, `@azmr/ui/theme-schema` exports `ThemeConfigSchema`, a Zod schema with a label and a help sentence on every field. Pass it to `fieldsFromSchema` from `@azmr/ui/zod` to describe the controls. The schema and `parseThemeConfig` give the same answer for every JSON value, and for the `undefined` fields that forms send; a test holds them to it on a table of cases and on thousands of generated ones.

## Apply the theme

A theme is a set of custom properties, so apply it to `<html>`, or to any element to theme only what is inside it:

```tsx
import { createTheme } from "@azmr/ui/theme";

const theme = createTheme({ primary: "#1E88E5", destructive: "#D32F2F" });

// Whole app: the variables as a style attribute, density as data-density.
<html lang="en-NZ" style={theme.cssVariables} {...theme.htmlAttributes}>

// One section only.
<section style={createTheme({ primary: "#7B1FA2" }).cssVariables}>…</section>
```

You can also emit the variables as CSS:

```ts example=css result=css
const theme = createTheme({ radius: "0.5rem", font: "Inter, sans-serif" });
const css = theme.css;
// => ":root {\n  --radius: 0.5rem;\n  --font-sans-stack: Inter, sans-serif;\n}"
```

To put the rule on one part of the page, such as a panel with its own branding, pass `scope`. It must be `:root`, one class, one id or one data attribute, and nothing that combines selectors, so a stored value cannot widen the rule beyond the element you named:

```ts example=scope result=firstLine
const firstLine = createTheme({ brand: "#0F4C5C", scope: ".org-theme" }).css.split("\n")[0];
// => ".org-theme {"
```

Where your Content-Security-Policy allows it (see below), prefer the `style` attribute: an inline style always wins. If you output `theme.css` in a `<style>` tag, put it **after** the `@azmr/ui` stylesheet. The tokens' own scopes (`.dark`, `[data-theme]`) have the same specificity as `:root`, so for the same element the later rule wins.

A theme's colours set on an outer element do not reach inside a nested `data-theme` or `.dark` scope, because that scope re-declares every colour token. Put the theme's variables on the scope element itself, or inside it.

### Under a strict Content-Security-Policy

A policy that allows styles only from your own origin and nonces (`style-src 'self' 'nonce-…'`, no `'unsafe-inline'`) blocks a `style` attribute in the HTML your server sends. A nonce can be put on a `<style>` element but not on an attribute, so the `style` prop shown above is blocked when it is rendered on the server. Send the theme as a `<style>` element with your nonce instead:

```tsx
<style nonce={nonce}>{theme.css}</style>
```

`theme.css` is built only from validated colours, sizes and font names, so it holds no markup, and React writes it as text. Put it after the `@azmr/ui` stylesheet. If your policy can allow `style-src-attr 'unsafe-inline'`, the `style` prop works too. Setting variables from client script with `element.style.setProperty` is never blocked.

To change one token by hand, override it for light and for dark:

```css
:root {
  --primary: oklch(0.55 0.2 260);
}

.dark,
[data-theme="dark"] {
  --primary: oklch(0.75 0.15 260);
}
```

## Dark mode

By default the page follows the operating system. The colours use OKLCH with `light-dark()` and `color-scheme: light dark`, so there is no JavaScript and no flash.

To force a mode, put `class="dark"` or `class="light"`, or `data-theme="dark"` or `data-theme="light"`, on `<html>` or on any element. Scopes nest: a `data-theme="light"` panel inside a dark page is light.

```html
<html data-theme="dark">
  <body>
    <aside data-theme="light">Always light, even on a dark page.</aside>
  </body>
</html>
```

Each scope declares every colour token explicitly instead of relying on `light-dark()` alone. Some bundlers (Next.js does, for older browser targets) rewrite `light-dark()` into variables that resolve where they are declared, which would stop a nested scope from changing anything. Declaring the colours in each scope works however the CSS is processed, and a test keeps those copies identical to `:root`.

### Remember the choice without a flash

Store the preference in a cookie and render it into `<html>` on the server, so the first paint is already right. This needs no inline script, so it works under a strict Content-Security-Policy:

```ts example=cookies result=attributes
import { htmlAttributes } from "@azmr/ui/theme";

const attributes = htmlAttributes.fromCookies("azmr-theme=dark; azmr-density=compact");
// => {"data-theme":"dark","data-density":"compact"}
```

Only known values are accepted. Anything else in the cookie is ignored, and `system` needs no attribute at all:

```ts example=cookies-invalid result=ignored
const ignored = htmlAttributes.fromCookies("azmr-theme=evil; azmr-density=huge");
// => {}
```

`ThemeProvider` and `useTheme()` change the theme and density on the client and write the cookie; see [Theme, density and locale](/docs/packages/ui#theme-density-and-locale) for a Next.js layout. A static site that cannot read cookies on the server can inline `themeInitScript()` instead; give the `<script>` tag your CSP nonce.

## Density

Density changes control heights, horizontal padding, gaps and row height together. Set `data-density="compact"` or `data-density="spacious"` on `<html>` or on any element; comfortable is the default and needs no attribute.

```html
<div data-density="compact">
  <!-- Buttons, inputs and table rows in here are compact. -->
</div>
```

The [token reference](/docs/guide/tokens#density-levels) lists the four values at each level. `createTheme` can set it too, through `htmlAttributes`:

```ts example=density result=attributes
const compact = createTheme({ density: "compact" }).htmlAttributes;
const comfortable = createTheme({ density: "comfortable" }).htmlAttributes;
const attributes = { compact, comfortable };
// => {"compact":{"data-density":"compact"},"comfortable":{}}
```

## Reduced motion

When the operating system asks for reduced motion (`prefers-reduced-motion: reduce`), every `--motion-duration-*` token collapses to `0.01ms` and the stagger step to `0ms`. A safety net also shortens other animations and transitions on the page. Reduced motion follows the system setting; the tokens have no per-subtree switch.

Mark motion that is genuinely essential, such as a spinner that shows work is happening, with `data-motion="essential"` to keep it. See [Motion](/docs/components/motion#tokens) for the motion tokens and what each component does.
